# 七升八暑期预习学习平台技术方案

关联产品设计：[暑期预习学习平台设计.md](暑期预习学习平台设计.md)。本方案采用“账号 + SQLite 服务端进度”架构，是前一版同步码快照方案的改进版。

## 1. 架构结论

SQLite 可以用于该任务系统，但需要澄清：现有同步服务本身已经使用 SQLite，继续沿用同一个数据库文件即可。需要替换的是以 8 位同步码识别用户、按 `deck_key` 整包覆盖进度快照的方式。新模块登录后按业务操作调用接口，由服务器在事务中只更新相关记录。

建议采用以下边界：

1. 暑期预习模块使用账号登录和操作级增量接口，不再接入 `ReviewSync` 快照同步，也不提供上传/拉取整包状态的接口。
2. 现有英语、语文卡片继续使用同步码和 `/api/sync/*`，首期不迁移，避免影响已经在用的页面。
3. 新旧接口运行在同一个 Python 服务和同一个 SQLite 数据库中，但使用不同数据表与 API 路径。
4. 后续验证稳定后，再决定是否把旧卡片逐步接入账号，不在暑期模块首版中同时改造。

对于当前单机部署、家庭或小规模学生使用，SQLite 足够：部署简单、事务可靠、备份方便。若未来需要多台 API 服务器水平扩容或持续高并发写入，再迁移 PostgreSQL；数据访问层不得依赖 SQLite 特有的业务语义，以保留迁移空间。


首版内容源只有现有八上英语结构化词库和账号自建任务。`book/` 是用户手动维护的排除目录，目录内任何文件都不进入发现、抽取、OCR、题库生成或容量计算；其他位置的无文本层 PDF 同样排除。以后只有排除目录之外的结构化数据或经检测存在有效文本层的资料才进入版本化 JSON 内容库。浏览器通过 `/summer-content/{contentVersion}/` 按需读取；线上版本内容持久化到 `/data/review-content/summer-preview/versions/`，Nginx 以只读静态路径映射，API 的 `SUMMER_CONTENT_DIR` 指向同一目录。已发布目录不可覆盖，只要仍有计划引用，部署和清理工具都不得删除对应目录。

`activity-host.js` 只负责加载单元、保存草稿和提交统一结果。每个题型模块实现固定协议：`mount(context)`、`getDraft()`、`restoreDraft(draft)`、`validate()`、`buildSubmission()`、`destroy()`；模块不得直接写进度或调用验收接口。每种后续题型先完成一个移动端样板和端到端测试，再加入正式 manifest。

## 3. 账号与安全

首期不开放任意公网注册。账号由管理员命令创建，或由一次性邀请码开通，避免公开注册带来的垃圾账号和运维负担。账号角色为 `student`、`reviewer`、`admin`；检查人通过账号关联表绑定一个或多个学生。用户名限制为 3-32 位 ASCII 字母、数字、点、下划线或连字符，转为小写后唯一；可选显示名不作为登录凭据。

开通、登录和修改密码时，浏览器将用户输入按 UTF-8 字节计算 MD5，并提交 32 位小写十六进制 `passwordMd5`。密码原文不写入浏览器存储、日志或请求字段。现代 Web Crypto API 不提供 MD5，前端需要内置经过测试且固定版本的本地实现，不从第三方 CDN 动态加载。

MD5 不是加密；前端 MD5 没有每用户盐，弱密码仍可能被彩虹表还原，`passwordMd5` 一旦泄露还可不经原文直接重放登录，因此它必须被视为等价密码。HTTPS 仍是强制要求，并确保 Nginx、应用、监控和错误追踪都不记录认证请求体。服务端不得把 MD5 直接保存到数据库，而是对 `passwordMd5` 的 ASCII 字节使用 Python `hashlib.scrypt`。`md5-scrypt-v1` 固定参数为：16 字节随机盐、`n=32768`、`r=8`、`p=1`、`dklen=32`，并为单次计算设置至少 64 MiB `maxmem`；数据库逐账号保存凭据方案、盐、参数和结果，校验时使用 `hmac.compare_digest`。未来升级参数时，成功登录后可重算为新方案。

由于服务器看不到密码原文，密码长度和复杂度只能由前端提示，不能作为可信的服务端安全约束；服务端只能严格校验 `passwordMd5` 为 32 位小写十六进制。服务端最多同时执行 2 个 scrypt 计算，超出请求排队或返回 `429`，避免线程和内存被登录请求耗尽。

会话令牌至少 32 随机字节，数据库只保存 SHA-256 令牌哈希。Cookie 名为 `__Host-review_session`，设置 `Path=/`、`HttpOnly`、`Secure`、`SameSite=Lax` 且不设置 `Domain`；空闲 14 天或绝对 60 天后失效，登录成功时生成新会话，修改或重置密码后撤销该账号其他会话。`GET /api/account/me` 返回绑定到当前会话的 CSRF 令牌，所有修改请求通过 `X-CSRF-Token` 提交，并校验 `Origin` 精确等于站点源。密码哈希只在开通、登录和修改密码时提交，后续学习接口只使用会话 Cookie。

登录同时限制为单用户名 5 次/5 分钟、单来源 IP 30 次/5 分钟；邀请码开通和密码重置按单邀请码/令牌 5 次、单来源 IP 10 次/10 分钟双重限制，避免家庭 NAT 下多个账号互相误伤。限流器必须有锁和过期键清理，不能直接复用当前无并发保护的 `RATE_BUCKET`。认证失败统一返回相同文案，避免枚举账号。请求体不得写入任何访问或错误日志。管理员命令支持：创建账号、生成邀请码、关联检查人与学生、停用账号、生成一次性密码重置令牌、撤销全部会话。首期不做邮件找回。

主要接口：

```text
POST /api/account/activate        使用邀请码开通账号
POST /api/account/login
POST /api/account/logout
GET  /api/account/me
POST /api/account/change-password
POST /api/account/reset-password

POST /api/summer/plans            开始第一轮并建立默认 60 天周期
GET  /api/summer/plan
POST /api/summer/plans/{id}/extend 检查人/管理员延长复习期
GET  /api/summer/today             纯读取，不创建任务
POST /api/summer/today/ensure      幂等生成当天任务组
POST /api/summer/custom-units      创建学生自建任务
PUT  /api/summer/tasks/{id}/choice
POST /api/summer/attempts
GET  /api/summer/review
GET  /api/summer/acceptance
GET  /api/summer/export
GET  /api/summer/students/{studentId}/checks
PATCH /api/summer/students/{studentId}/checks/{checkId}
```

所有 `/api/summer/*` 业务写请求和检查确认请求携带客户端生成的 `eventId`；登录、退出等认证接口不使用该字段。服务端对 `(user_id, event_id)` 建唯一约束；每条幂等记录同时保存请求体规范化后的 SHA-256、响应状态码和响应 JSON。收到重复 `eventId` 时，先于行版本检查处理：请求哈希相同则返回第一次的原始响应，请求哈希不同则返回 `409 IDEMPOTENCY_KEY_REUSED`。因此第一次提交成功但响应丢失时，重试仍得到相同成功结果。

账号接口请求约定：

```json
{
  "username": "student01",
  "passwordMd5": "32位小写十六进制字符串"
}
```

服务端拒绝明文密码字段、非小写 MD5、缺少 HTTPS 转发标记的生产请求。登录成功后设置会话 Cookie，响应体不返回密码哈希、会话令牌或数据库凭据。

`sync_api/openapi.yaml` 是接口契约的唯一来源，必须定义每个接口的请求、成功响应、权限、CSRF、`eventId`、行版本和示例。错误统一为：

```json
{
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "任务已在另一设备更新",
    "requestId": "服务端请求标识",
    "details": {}
  }
}
```

固定使用 `400/401/403/404/409/422/429/500` 的语义；前端只能依据稳定的 `error.code` 分支，不解析中文文案。日期为 `YYYY-MM-DD`，时间为 UTC RFC 3339，列表接口统一使用游标分页。

## 4. 操作级增量更新

新模块没有“上传全部进度”和“拉取全部进度”按钮。页面进入时按需读取今日任务、某学科进度或验收汇总；发生修改时立即调用与该动作对应的接口。登录密码不参与学习操作请求。

典型写操作：

| 用户操作 | 接口 | 只允许修改的数据 |
| --- | --- | --- |
| 开始计划 | `POST /api/summer/plans` | 新建计划、核心单元快照和周期日期 |
| 生成今日安排 | `POST /api/summer/today/ensure` | 幂等创建当天任务组与明细 |
| 创建自建任务 | `POST /api/summer/custom-units` | 新建当前账号可见的通用学习单元 |
| 选择/替换任务 | `PUT /api/summer/tasks/{id}/choice` | 指定任务槽位及其行版本 |
| 提交测验 | `POST /api/summer/attempts` | 新建答题记录，并推进对应任务、单元和复习阶段 |
| 检查人确认纸笔项目 | `PATCH /api/summer/students/{studentId}/checks/{checkId}` | 已授权学生的指定检查项及其行版本 |
| 延长复习期 | `POST /api/summer/plans/{id}/extend` | 只增加有效结束日期并写审计记录 |

提交测验的请求包含 `eventId`、`taskId`、`unitId`、`contentVersion`、逐题答案和作答时间，不接受客户端直接传入的最终得分或`已通过`状态。服务器从内容索引重新判分，并在同一事务中：

1. 校验或预留幂等事件键；重复事件按既定响应直接返回。
2. 写入 `attempts`，更新对应 `daily_tasks` 和 `unit_progress`。
3. 根据结果创建、完成或顺延 `review_schedule`。
4. 构造更新后的任务、单元进度、下次复习日期和最新行版本。
5. 在同一事务提交前，把请求哈希、响应状态码和完整响应 JSON 写入幂等事件记录；提交后返回该响应。

`GET /api/summer/today` 始终是纯读取：当天数据不存在时返回空任务组和 `needsEnsure: true`。学生页面仅在明确进入今日任务后调用 `POST /today/ensure`；该 POST 使用 `eventId`，重复调用返回同一结果。浏览器预取、监控和爬虫 GET 不会创建任务或获取写锁。

前端收到成功响应后只替换响应涉及的本地视图记录。网络失败时保留当前答案并使用同一 `eventId` 重试；`409` 表示行版本冲突，前端重新读取对应记录后由用户再次确认。API 不接受包含全部 `units`、`attempts` 或计划状态的通用 PUT 请求，从接口边界阻止整包覆盖。

## 5. SQLite 数据模型

沿用当前数据库文件，但新增版本化表。所有时间保存 UTC，计划日期另存 `Asia/Shanghai` 时区下的学习日期。

| 表 | 作用 | 关键约束 |
| --- | --- | --- |
| `users` | 账号、角色、凭据方案、scrypt 哈希、盐和状态 | 规范化用户名唯一 |
| `user_links` | 检查人与学生的授权关系 | `(reviewer_id, student_id)` 唯一且角色合法 |
| `invitations` | 一次性邀请码 | 邀请码哈希唯一、过期时间、使用人 |
| `sessions` | 登录会话 | 令牌哈希唯一、到期与撤销时间 |
| `content_versions` | 不可变内容版本及发布状态 | `content_version` 唯一 |
| `study_plans` | 第一轮与复习周期 | 保存 `first_round_end_date`、`original_review_end_date`、`effective_review_end_date` |
| `plan_units` | 本期核心单元快照 | `(plan_id, unit_id)` 唯一，保存内容版本 |
| `custom_units` | 学生/检查人创建的通用任务 | 所属学生、学科、预计分钟和检查方式 |
| `daily_slots` | 每日复习组/主学习等展示组 | `(plan_id, study_date, slot_type)` 唯一，保存预计分钟 |
| `daily_tasks` | 槽位内的具体任务 | `(slot_id, position)` 唯一，可关联复习计划 |
| `unit_progress` | 单元状态与复习阶段 | `(plan_id, unit_id)` 唯一，带行版本号 |
| `attempts` | 每次测验结果和错题 | `event_id` 幂等，保留得分与题目版本 |
| `review_schedule` | 到期复习任务 | 单元、阶段、到期日和完成状态 |
| `paper_checks` | 待检查/已检查、检查人和时间 | `(plan_id, activity_id)` 唯一 |
| `idempotency_records` | 请求哈希和响应快照 | `(user_id, event_id)` 唯一，90 天后可清理 |
| `audit_events` | 计划调整、检查和账号安全审计 | 只保存必要元数据，不保存完整响应 |
| `schema_migrations` | 已执行迁移 | 迁移版本唯一 |

每次创建 SQLite 连接都执行 `PRAGMA foreign_keys=ON`、设置 `busy_timeout=5000`，数据库初始化时启用 `WAL`。写操作使用短事务；需要先读后写的任务生成、提交测验和幂等处理使用 `BEGIN IMMEDIATE`，遇到 `SQLITE_BUSY` 按有限退避重试，禁止在事务内执行 scrypt、读取大文件或调用外部服务。所有“提交测验 -> 更新进度 -> 创建下次复习”操作放在同一事务中。修改任务选择和检查状态时使用整数 `version` 做乐观并发控制；版本不匹配返回 `409`，客户端刷新后重试，避免后一台设备静默覆盖前一台设备。

幂等记录和审计记录分开维护。后台每日分批删除创建超过 90 天且没有进行中请求的 `idempotency_records`；90 天足以覆盖客户端重试窗口。`audit_events` 按安全与验收需要保留精简字段，并由管理员策略决定保留期，避免长期存储完整响应 JSON 导致数据库膨胀。

部署前自动备份数据库，迁移成功后才重启服务。WAL 模式下不得用普通文件复制作为一致性备份，必须使用 SQLite Online Backup API 或 `VACUUM INTO`。生产环境每日保留数据库快照，并定期执行 `PRAGMA integrity_check` 和恢复演练。

## 6. 第一轮与复习周期规划

创建计划时，服务器把当前结构化英语核心单元和学生/检查人已选择的自建核心任务写入 `plan_units`，形成第一轮范围；以后新增任务默认是拓展任务，纳入核心必须通过容量检查并记录调整人。内容库更新不会悄悄改变已经开始的计划。浏览器和服务器都从计划固定的 `contentVersion` 读取结构化内容；存在计划引用的版本不得删除。

开始计划当天是第 1 个自然日，`first_round_end_date` 为开始日期加 44 天；默认 `original_review_end_date` 为开始日期加 59 天，即总周期 60 天。`currentDay` 不入库，由服务器按 `Asia/Shanghai` 日期计算。第一轮可跨到开学后，不以暑假日期硬截断。

检查人或管理员可调用延长接口把 `effective_review_end_date` 向后增加，每次延长 1-30 天且必须填写原因；可多次延长，不设置业务总上限。延长只改变后续复习安排，不修改原第 45 天第一轮快照、原第 60 天掌握率和历史任务。没有延长时，有效结束日等于默认第 60 天。

任务由服务器生成，保证多设备结果一致：

| 天数 | 系统行为 |
| --- | --- |
| 第 1-7 天 | 建立英语、自建任务和复习节奏 |
| 第 8-40 天 | 推进核心单元第一轮，同时完成到期复习和补测 |
| 第 41-45 天 | 第一轮收口，优先完成尚未首学的核心单元 |
| 第 46-60 天 | 集中复习、补测、待检查和最终验收 |
| 第 60 天后 | 仅在计划被延长时继续安排未通过项 |

规划器以预计分钟为主约束，首页最多展示 5 个 `daily_slots` 只是界面约束。正常日创建一个 8-15 分钟的`今日复习组`，把同学科到期卡、错题和补测按“补测优先、逾期天数降序、错误次数降序、到期时间升序”打包为组内 `daily_tasks`；再安排 20-30 分钟主学习、10-15 分钟辅助任务和可选阅读，总预计时长控制在 45-60 分钟。

正常复习预计超过 15 分钟，或连续两天存在未完成核心任务时，统一进入`恢复模式`：复习组预算可提高到 30 分钟，当天最多再安排一个新学任务，总预计时长不超过 70 分钟。超出当日预算的复习保留原到期日并在下一天继续优先。不存在“到期任务达到 5 个”和“连续两天未完成”两套不同恢复机制。

学生可对新学组选择系统推荐、继续昨天或自己选择；复习和补测不可替换。`GET /today` 只读取，`POST /today/ensure` 在 `BEGIN IMMEDIATE` 事务中创建尚不存在的任务组；重复 POST 或多设备同时调用都返回同一批记录。

首版纸面容量为：英语 6 个教材单元拆成约 12 个词汇/短语包，预计首学 150-180 分钟；其他学科自建核心任务首学合计不超过 1,200 分钟；第一轮首学总量建议不超过 1,350 分钟。45 天另预留约 675 分钟正常复习及至少 20% 恢复缓冲。添加核心任务时实时校验，超出预算只能设为拓展，或由检查人延长后纳入。

以后新增自动内容时，发布前用真实规划器模拟完整周期：每个核心单元提供 `learnMinutes`、`reviewMinutes` 和 `remedialMinutes`；模拟至少包含一次首学、三次复习、每单元一次补测和额外 10% 缺席缓冲，并验证全部首学尽量在第 45 天完成、全部复习在默认第 60 天或明确延长期内完成。失败则禁止发布。

## 7. 复习状态机与验收

单元状态为：`not_started`、`learning`、`review_due`、`remedial`、`check_pending`、`passed`。单元验收类型为 `auto`、`paper` 或 `mixed`。自动判分统一使用 `correct / total >= 0.8`；自动验收单元至少包含 5 个独立计分项，题量不足时内容校验器阻止发布，避免 80% 规则失真。

自动测验的成功间隔依次为 1、2、4 天。所有间隔从最近一次成功完成阶段的学习日期起算；如果发生补测，后续日期整体顺延：

```text
首轮 >= 80% -> stage=1，1 天后复习
首轮 < 80%  -> remedial，pending_stage=0，次日补测
阶段 1 >= 80% -> stage=2，2 天后复习
阶段 2 >= 80% -> stage=3，4 天后复习
阶段 3 >= 80% -> 自动测验部分完成
任一阶段 < 80% -> remedial，pending_stage 保持该阶段，次日补测
补测 >= 80% -> 当前 pending_stage 视为完成，按上述规则进入下一阶段
补测 < 80%  -> 保持 remedial，次日继续补测
```

`unit_progress` 保存 `review_stage`、`pending_stage`、`next_review_date`、`last_score`、`auto_completed_at` 和 `version`；`attempts` 保存每次结果，不能只保留最近一次。

纸笔活动完成时生成`待检查`记录。学生没有修改权限；关联检查人完成检查和必要订正后改为`已检查`，记录 `checked_by`、`checked_at` 和行版本。`paper` 单元在全部纸笔项已检查后进入 `passed`；`mixed` 单元必须同时满足自动测验部分完成和全部纸笔项已检查，否则保持 `check_pending`；`auto` 单元完成阶段 3 后直接进入 `passed`。

验收分为两个不可互相覆盖的快照：第 45 天或提前完成时记录`第一轮完成率`，只判断核心单元是否完成首次学习；默认第 60 天记录`最终掌握率`。最终通过要求全部核心单元为 `passed`、没有逾期复习、没有需补测单元和待检查项目。未通过时可在延长期继续补完，但不得回写或美化原第 45/60 天快照。

## 8. 英语单词与旧页面关系

英语词库必须只有一个内容源。建议把八上词汇整理为规范 JSON，并通过内容工具生成旧单词卡可直接加载的 `renai-grade8s-words.js`。旧页面显示和旧进度键保持不变；暑期模块使用同一词库内容，但成绩写入账号下的 `unit_progress`。

旧单词卡的“已掌握”不能直接算作暑期任务通过，因为它没有 80% 测验和第 1、3、7 天复习记录。可提供一次性“导入旧进度作为已学习提示”，导入后仍需完成一次分级测验才进入正式复习阶段。

## 9. 内容制作与加载

首页只加载轻量 `manifest.json`；进入某一学科或单元时再从 `/summer-content/{contentVersion}/` 加载对应 JSON 和媒体。发布流程先把新版本上传到独立内容目录并完成校验，再原子更新网页顶层 `manifest.json` 的当前版本指针；禁止修改已发布目录。内容版本状态为 `draft/published/retired`，只有没有计划引用的 `retired` 版本才可由清理命令删除。

新增 `tools/validate_summer_content.py`，在部署前检查：

1. 单元、活动和题目 ID 全局唯一且格式稳定。
2. 前置单元、题目、答案、解析和媒体引用均存在。
3. 第一轮首学容量和默认 60 天复习容量均通过规划器模拟。
4. 自动验收单元题量达到最低要求，80% 边界可计算。
5. 结构化来源标识完整；图片尺寸、体积和热点坐标有效。
6. 生成服务端内容索引和旧英语页面使用的数据脚本。
7. 新版本目录完整、内容哈希一致，且不会覆盖仍被计划引用的版本。

内容发现工具在遍历阶段直接跳过整个 `book/` 子树，不枚举其中的文件，也不因文件类型或文本层状态改变该规则。对其他位置的 PDF 先检查文本层；提取后去除空白仍为 0 字符的文件直接标记 `ignored_no_text`，不做 OCR、不渲染录入、不进入后续管线。当前资料包根目录 16 份 PDF 均属于该状态。

结构校验通过后，还需由人工检查题目和答案，记录 `reviewedBy/reviewedAt` 后才能标记为 `published`。内容渲染统一转义文本，只有经过白名单处理的字段允许富文本，防止题库内容破坏页面结构。

## 10. 客户端缓存与网络异常

服务器是权威进度源，浏览器使用 IndexedDB 缓存今日任务和当前内容。提交时先生成 `eventId` 并显示“正在保存”；服务器确认后显示“已保存”。网络中断时保留当前答案草稿，但首版不自动推进任务状态，也不把尚未确认的操作显示成已完成。

客户端不能在未登录时把缓存状态判为正式完成。退出账号时清除该账号的学习缓存；不同账号使用独立缓存命名空间。恢复网络后，用户可用原 `eventId` 手动重试提交。若服务器返回 `409`，客户端重新获取最新任务和进度并提示用户，不静默覆盖。

网络失败时必须做到：不丢失当前答案、明确显示“尚未保存”，并允许手动重试。首版不实现后台自动离线队列，减少乱序重放和跨设备冲突；后续确需离线提交时再基于同一 `eventId` 协议扩展。

## 11. 兼容与部署

现有 `/api/sync/*` 路由、`progress_records` 表和同步码全部保留。Nginx 代理范围从 `/api/sync/` 扩展为 `/api/`，仍指向同一服务端口；旧接口路径和响应不变。新增 `location ^~ /summer-content/` 只读 `alias`，指向 `/data/review-content/summer-preview/versions/`；必须使用 `^~`，避免现有图片静态正则绕过该映射。systemd 服务增加 `SUMMER_CONTENT_DIR=/data/review-content/summer-preview/versions`，目录归属 `www-data` 且内容文件只读。

仅对新模块和新 API 增加安全响应头，避免破坏包含内联脚本的旧页面：`Content-Security-Policy` 至少限制 `default-src/script-src/style-src/connect-src/img-src` 为本站需要的来源并设置 `frame-ancestors 'none'`，同时启用 `X-Content-Type-Options: nosniff`、严格 `Referrer-Policy` 和 HSTS。新模块脚本与样式全部使用外部文件，不依赖 `unsafe-inline`。

现有部署脚本会删除并重建整个网页目录，因此不可把版本化内容只保存在远端 webroot。部署顺序调整为：备份 SQLite -> 将新内容版本以“目录不存在时才允许创建”的方式上传到持久内容目录 -> 运行内容校验 -> 上传静态页面和 API 代码 -> 执行数据库迁移 -> 原子更新当前内容指针 -> 重启服务 -> 检查旧同步接口 -> 检查账号登录与今日任务。任一步失败应停止发布，不删除旧数据库、旧静态页面或仍被引用的内容版本。

账号系统稳定后，可另立项目逐步迁移旧卡片：登录用户把旧 `deck_key` 数据归属到账号，未登录用户继续使用同步码。暑期模块不等待这项迁移。

## 12. 功能分期

每一阶段必须是可部署、可保存真实进度的纵向切片，不用临时 localStorage 数据替代正式接口：

| 阶段 | 必须交付 | 暂不包含 |
| --- | --- | --- |
| 首个可用版本 | 管理员建学生账号、登录会话、数据库迁移、操作级增量接口、自建任务、英语词卡、今日复习组、答案草稿 | 邀请码、完整推荐、其他自动题型 |
| 第二版本 | 检查人账号与 `reviewer.html`、账号关联、纸笔检查、第一轮/掌握率、计划延长、导出 | 批量内容导入 |
| 第三版本 | 完整规划器、恢复模式、容量模拟、邀请码、内容版本发布和清理工具 | 未通过样板验收的题型 |
| 后续题型版本 | 每次只加入一个通过移动端与端到端测试的题型适配器 | 无文本层 PDF 的 OCR 或人工看图录入 |

首个可用版本上线后即可创建第一轮计划，后续版本只能增加能力，不得改变已有 `eventId`、进度状态和内容版本的语义。

## 13. 测试与完成标准

自动测试至少覆盖：

1. 日期边界、时区、第 45/46/60 天、延长周期和第一轮快照保持。
2. 多个复习同时到期、按学科分组、分钟预算、5 个展示组上限、顺延和统一恢复模式。
3. 80% 临界值、首测失败、各阶段失败、连续补测、纸笔及混合单元的最终通过状态。
4. 两台设备同时修改的版本冲突；同 `eventId` 同请求返回原响应、不同请求返回冲突；网络失败后的草稿保留与手动重试。
5. MD5 输入格式、固定 scrypt 参数、并发计算上限、邀请码、登录限流、会话到期/撤销、CSRF 和账号间数据隔离。
6. 学生越权确认检查、未关联检查人访问、检查人正常确认及 `checked_by` 审计。
7. SQLite 迁移、每连接外键、繁忙重试、事务回滚、在线备份恢复和旧 `/api/sync/*` 回归。
8. `book/` 与无文本层 PDF 被排除；内容重复 ID、悬空引用、无答案题目、媒体缺失、核心容量超限、旧计划继续读取旧内容版本。
9. 每个题型适配器的草稿恢复、校验、提交和销毁协议。
10. OpenAPI 请求/响应契约测试，以及桌面和移动端完成“登录 -> 开始计划 -> 选择任务 -> 测验 -> 次日复习 -> 检查 -> 延长 -> 验收”的端到端流程。

实现完成的标准：账号可安全开通和登录；第一轮约 45 天、默认复习到第 60 天且可审计延长；核心范围及内容版本固定且容量可行；复习能按时间预算分组和顺延；任务在多设备上保持一致；80% 与第 1、3、7 天复习正确推进；检查权限和纸笔验收有效；网络重试返回一致结果且不会重复计分；OpenAPI 与实现一致；旧卡片同步功能无回归。
