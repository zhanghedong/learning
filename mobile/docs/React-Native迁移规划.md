# Review：HTML 到 React Native 迁移规划

日期：2026-10-26  
状态：规划稿，基于当前仓库代码梳理；本次只建立文档，不初始化应用或改动线上服务。已按代码核对评审修订（条目键、古诗文快照与排序、合规依赖、部署路由、同步合并、期中计划范围与排期）。

## 1. 目标与实施结论

在仓库内新增独立的 `mobile/` 应用，使用 React Native + Expo + TypeScript，实现 Android 和 iOS 原生学习体验。先迁移现有学习闭环，再考虑新功能。第一轮推荐以 Android 真机跑通完整流程，同时保持 iOS 可构建，并在发布前完成双端真机验证。

采用“提取内容与业务规则、重写界面、兼容旧进度”的方式：教材内容、卡片筛选规则和古诗文复习算法可以复用；DOM、CSS、浏览器存储、浏览器朗读和剪贴板交互需要替换。WebView 仅可用于短期对照验证，不作为最终学习界面。

Web 与 Mobile 在迁移期并行。新增手机号或邮箱登录与账号管理，学习进度统一归属账号，登录后自动恢复和同步。现有 Python + SQLite 服务需要扩展认证与账号进度接口；旧同步码仅作为可选历史导入渠道，不再作为新用户的登录或日常同步方式。

默认范围：手机优先、平板适配、离线学习、原有教材、手机号/邮箱账号登录、账号进度同步和可选旧进度迁移。Windows/macOS 原生客户端、统一 Web 重写、语音自动评分和暑期学习平台扩建暂不纳入。2026 期中计划的最后日期为 2026-11-06，早于移动端可交付时间，本轮不做原生迁移，保留在网页。

### 2.2 需要保持的真实行为

**词卡：** 按单元/课筛选、切换正反方向、翻面、上一张/下一张、已掌握/需复习标记、查看全部、统计、上次位置恢复、范围重置、进度导入导出。英语词卡额外有系统 TTS 发音及开关；语文字词展示汉字和带声调拼音。

各套词卡条目字段不同：闽教三下、四上和专项英语为 `[英文, 释义]`；仁爱七下为 `[英文, 释义, 词性]`（短语无词性）；仁爱八年级为 `[英文, 释义, 词性, 音标]`；语文字词为字词与拼音。通用引擎的数据模型和展示需允许字段缺省。

词卡状态为 `got`、`review`，键不存在表示未学。不得将“查看答案”自动当作已掌握。

**古诗文：** 导学、正文点词、分段遮挡记忆、首次检测、按轮复习、全文阅读、统计、导入导出和同步。逻辑主要位于 `web/assets/grade8a-recitations.js`；正文和词义位于 `web/assets/data/pep-chinese-grade8a-required-recitations.json`，导学与部分分段规则仍嵌在 JS 中，提取时必须一并处理。

当前掌握阶段标签实际为 `未学习 / 刚学过 / 有印象 / 已掌握`。题目生成、升降级、同轮重复、提示惩罚和结束条件应以代码与固定样例为迁移基线，不能直接照旧设计文档重写。当前 `ui.quiz`、`ui.round` 主要是内存态，App 若新增中断恢复，需要作为明确增强单独验收。

现有算法不使用随机数：轮次队列按 `(3 - stage) * 100 + wrong * 8 + hashString(id + roundId) % 13` 排序，选项按 `hashString(选项 + seed)` 排序；`hashString` 为基于 UTF-16 `charCodeAt`、`Math.imul` 和 `>>> 0` 的 FNV-1a。`roundId` 来自持久化并参与同步的 `roundCounter`。移植时必须逐位复刻该哈希与排序比较，相同 `roundCounter` 和状态下的题序应与 Web 完全一致。

**期中计划（本轮不迁移）：** 固定计划内容、按日期展示和任务勾选，使用 `midterm-plan-checks-v1` 本地存储；当前未接入 `ReviewSync`，也没有导出。任务键为 `t-${date}-${t[3] 或任务下标}`：未显式标识的任务依赖下标，且睡前阅读任务通过运行时插入并给就寝任务补写 `t[3]` 来保持旧勾选。计划于 2026-11-06 结束，本轮保留网页；以后若做通用计划模块，提取时须连同运行时插入逻辑一起固定任务键。

### 2.3 现有同步能力与限制

- 客户端：`web/assets/sync.js`，同步码保存在 `review_sync_code_v1`。
- 服务端：`sync_api/server.py`，Python 标准库 HTTP 服务 + SQLite。
- 接口：`POST /api/sync/create`、`GET /api/sync/progress`、`PUT /api/sync/progress`。
- 同步维度：`code + deck_key`；进度包主要包含 `app/deckKey/status/pref/updatedAt`。
- 古诗文复用同一进度包字段但含义不同：`status` 为 `state.items`（每项 `{stage, correct, wrong, lastCorrectRound, lastSelf}`），`pref` 为 `{pieces, ui, roundCounter}`；词卡的 `status` 才是 `got/review` 映射。
- 当前为整份快照覆盖，没有修订号、条件更新、逐条合并或服务端历史版本。
- Web 端定时检查快照变化并延迟上传；启动时自动拉取。移动端应改为状态变更触发和生命周期触发。
- 后端请求体上限为 256 KiB；古诗文恢复草稿、长作答记录不能无限塞入同步快照。
- 服务端限流使用 `self.client_address[0]`，部署在 Nginx 后时始终为 `127.0.0.1`，实际是全站共用限流桶；`RATE_BUCKET` 为进程内普通字典，多线程下不安全且重启清空。服务基于标准库 `http.server`，官方不建议用于生产。
- Nginx 配置域名为 `review.studynote.me`，`deploy/nginx/review.studynote.me.conf` 只转发 `/api/sync/`，`client_max_body_size 256k`。本次没有验证线上可用性，开发时需做真实接口连通验证。

## 3. 原生产品结构

建议一级导航为“学习库”和“我的”，教材内使用栈导航。第一版不设一个没有统一算法支撑的“全部待复习”总入口。

```text
学习库
├─ 继续学习
├─ 英语教材 / 语文字词 / 古诗文 / 专项
├─ 词卡：范围 → 学习 → 本组统计
└─ 古诗文：总览 → 首次学习 / 轮次复习 / 全文
我的
├─ 未登录：登录 / 注册（手机号或邮箱）
├─ 账号管理：昵称、手机号、邮箱、登录设备、退出 / 注销
├─ 云端进度：同步状态、最后同步时间、失败重试
├─ 历史数据导入：旧同步码 / 导出文本（可选）
├─ 导入、导出、备份恢复
└─ 字号、朗读、应用信息
```

交互约定：

1. 点击翻面，按钮始终可完成切换与标记；滑动可作为增强，不能成为唯一操作方式。
2. 筛选使用原生选择面板，注释使用底部面板；长文使用可滚动正文，底部操作避开安全区与键盘。
3. 语文保留暖纸色和重点词强调，英语优先保证单词、词性、释义的层级。样式转换为设计 token 与 `StyleSheet`。
4. 长单词、长短语和大字号允许换行；不靠无限缩小字号容纳内容。操作触控区域目标至少 44×44。
5. 手机单列，平板按可用宽度显示目录和正文；不使用设备型号判断布局。
6. Android 返回键先关闭面板，再返回页面；练习中离开提供保存/退出选择。

### 3.1 注册、登录与账号管理

“我的”页提供固定账号入口，学习库顶部也可展示“登录后同步进度”。建议采用以下首版流程，手机号和邮箱均为必交付登录渠道：

1. 选择手机号或邮箱 → 输入标识 → 发送验证码 → 输入验证码 → 登录。未注册标识在验证成功后创建账号，页面提前告知“未注册将自动创建账号”。手机号采用国家/地区码 + 号码。
2. 首版建议使用短信验证码或邮箱验证码免密码登录，减少记忆和找回密码成本；该方式是规划默认选择。密码登录如后续需要，另增密码设置、修改与找回流程。
3. 用户无需同时提供手机号和邮箱。登录后可在账号管理中绑定另一种登录方式，两种方式指向同一个稳定 `user_id`。
4. 绑定、换绑、注销需要近期身份验证；新手机号/邮箱也必须验证。解绑后至少保留一种可用登录方式。目标标识已属于另一账号时提示冲突，首版不自动合并账号。
5. 账号管理包含昵称、脱敏手机号/邮箱、绑定与换绑、当前登录设备、退出其他设备、退出登录、账号注销。普通用户不具备查看或管理其他用户账号的权限；后台管理系统暂不纳入。
6. 未登录可作为游客离线学习；首次注册/登录需要联网。登录时检测游客进度，由用户选择导入当前账号或保留游客档案；账号已有同教材进度时先预览差异和备份，再选择保留哪份，不静默覆盖。
7. 已登录用户断网可继续使用本机已缓存进度，恢复网络后续传。会话失效时保留待同步数据并提示重新登录，不把账号数据转成游客数据。
8. 退出或切换账号停止旧账号上传与在途结果应用，清除本机登录凭据；本地缓存、草稿和待上传记录按账号隔离。存在未同步进度时提示后果，并提供先同步或保留隔离副本的选项。
9. 换手机后使用已绑定手机号或邮箱登录，即可获取该账号教材进度列表并恢复；日常使用无需记录同步码或逐教材手动搬运。手机号和邮箱均不可用时，不承诺自动找回，应提示提前绑定备用方式。

### 3.2 账号实现边界

验证码通过服务端接入短信和邮件服务商发送，发送密钥仅存服务端。开发环境可使用受控测试通道，生产不得保留固定万能验证码。短信签名/模板、邮件发信域名和供应商开通是实施依赖，在 P0 第一天启动办理（见 §3.3）。

验证码建议有效期 5 分钟、重发间隔 60 秒、单次最多尝试 5 次，并按标识、设备及 IP 设置发送配额和错误次数限制；客户端 IP 只从可信反向代理设置的 `X-Real-IP` 读取，不使用连接地址（经 Nginx 时恒为 `127.0.0.1`），也不信任客户端自带的转发头。限流计数持久化到数据库或共享存储，保证多线程安全、重启不清零。发送验证码前接入人机验证，防止短信轰炸和刷量费用；新验证码使旧码失效。验证码须绑定用途与目标，服务端采用带服务端密钥的摘要保存，成功校验与消费在事务中完成，过期或使用后不能重放。界面统一提示，避免通过发送响应枚举已注册账号。

会话建议采用短期 access token + 可撤销、轮换的 refresh token；App 将 refresh token 存于系统安全存储，服务端仅存其摘要。并发刷新由客户端串行化，服务端检测旧 refresh token 重放并撤销相应会话；退出、远程下线和注销使会话失效。所有账号进度请求从会话确定 user_id，不信任客户端传入的用户 ID。Web 接入时另行落实安全 Cookie 与 CSRF 防护，不把 refresh token 放进 localStorage。

账号注销需再次验证、展示删除范围和未同步提示；完成后撤销会话、清除该账号云端进度与当前设备缓存，服务端备份保留/到期清除规则向用户说明。其他离线设备联网后识别账号失效并清理缓存，不能承诺即时远程擦除离线设备。

认证、换绑与会话设计参考 [OWASP 认证指南](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)和[邮箱验证指南](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html)。

### 3.3 上架与合规依赖

以下事项办理周期不受开发控制，可能决定首个试用版的时间，须在 P0 第一天启动，不等 P0 结束：

- **App 备案：** 国内安卓应用市场上架需要 App 备案；iOS 在国内 App Store 上架同样要求备案信息。备案依赖已备案的主体与域名。
- **短信资质：** 短信签名与模板审核通常要求企业主体或已备案的网站/App，个人主体可能无法申请。若短期办不下来，首个试用版只开放邮箱验证码登录，手机号登录在资质到位后上线；手机号仍属于正式发布的必交付渠道。
- **未成年人个人信息：** 目标用户是中小学生，手机号、邮箱和学习记录属于未成年人个人信息。需要隐私政策、用户协议、首次启动的同意流程，不满 14 周岁的用户需取得监护人同意；收集范围保持最小，个人信息处理规则与账号注销说明一致。
- **商店要求：** 提供账号注册即需提供 App 内账号注销（§3.1 已包含）；隐私标签与权限说明在发布时按商店现行要求核验。

## 4. 技术方案

### 4.1 推荐技术栈

| 层 | 建议 | 本项目用途 |
| --- | --- | --- |
| 应用 | React Native + Expo + TypeScript | 双端原生 UI、统一构建 |
| 路由 | Expo Router | 教材、篇目、学习会话路由 |
| 状态 | React hooks + Context，复杂流程用 reducer | 卡片会话、答题状态机；首版控制依赖数量 |
| 本地持久化 | `expo-sqlite` | 进度、草稿、同步队列、备份元信息 |
| 朗读 | `expo-speech` | 替换浏览器 `speechSynthesis` |
| 导入导出 | Expo 文件选择、文件系统、分享及剪贴板模块 | 文件备份和粘贴旧进度 |
| 登录凭据 | 系统安全存储，建议 Expo SecureStore | 保存 refresh token；验证码、token 和旧同步码不写日志 |
| 账号服务 | Python + SQLite，新账号接口改用成熟 Web 框架（如 FastAPI/Starlette，P0 确定），接入短信与邮件发送适配器 | 注册登录、身份绑定、会话、账号注销与进度鉴权 |
| 测试 | 纯逻辑测试 + React Native 组件测试 + 真机关键流程 | 验证规则、交互和平台行为 |

Expo Router 提供基于文件的路由；Expo 提供 SQLite 与 TTS 模块，适合此项目的数据与设备能力需求。依据：[Router 文档](https://docs.expo.dev/router/introduction/)、[SQLite 文档](https://docs.expo.dev/versions/latest/sdk/sqlite/)、[Speech 文档](https://docs.expo.dev/versions/latest/sdk/speech/)。本方案选择本地读写优先，与 Expo 的[本地优先架构说明](https://docs.expo.dev/guides/local-first/)方向一致；同步冲突策略仍需自行实现。

不在规划稿中固定 SDK 版本。初始化时选择稳定 Expo SDK，使用其匹配的 React Native 版本和 `expo install` 安装原生依赖，提交锁文件，并验证 development build；不能只以 Expo Go 可运行作为完成依据。

| --- | --- | --- |
| `deck_progress` | `profile_id, deck_key`；kind、schema_version、content_version、payload_json、local_revision | 每教材完整持久化快照 |
| `session_drafts` | `profile_id, deck_key`；session_json、content_version | 本机答题队列、题序、答案、提示状态和当前位置 |
| `sync_state` | `profile_id, deck_key`；base_json、server_revision、acked_revision、inflight_revision、inflight_payload_json、last_success_at | 共同基线（三方合并用）、已确认与在途版本 |
| `backup_snapshots` | ID；profile_id、来源、教材、创建时间、payload_json | 导入、重置、拉取覆盖前备份 |
| `schema_migrations` | version | 本地数据库升级 |

profile_id 使用本地游客 ID 或服务端稳定 user_id，不使用手机号/邮箱作为进度主键；换绑不能改变进度归属。备份表也必须包含 profile_id，所有缓存查询与在途请求都校验当前账号。

同步按整份快照进行，因此不单设 outbox 表：每次有效变更在一个事务内写入 `deck_progress.payload_json` 并递增 `local_revision`，持久化失败时不展示“已保存”。`local_revision > acked_revision` 即为待上传；上传时把当时的 revision 与快照写入 `inflight_*`，响应回来只把 `acked_revision` 推进到该在途 revision，期间产生的新变更仍保持待上传。同一教材同时只有一个在途请求，未发送的多次变更天然合并为最新快照。草稿按内容版本恢复；不兼容时保留备份，回到最近安全步骤。

首版可将进度保存为 JSON 快照，避免过早把每个题型拆成大量表。跨教材统计变慢时再增加索引或明细表。

## 5. 内容提取与 ID 兼容

### 5.1 提取流程

1. 从五个英语 HTML 和一个中文字词 HTML 提取 `DATA`，输出严格 JSON。`DATA` 是 JS 对象字面量（属性名不带引号），不能按 JSON 直接解析，也不宜用正则；使用 JS AST 解析器（如 acorn）只取 `const DATA` 的字面量节点求值，避免对整页执行 `eval`。
2. 提取古诗文 JSON、`GUIDES`、`POEM_TITLES` 诗歌分类和 `CUSTOM_CHUNK_MARKERS` 自定义分段规则，固定现有生成结果。
3. 建立 manifest：`deckKey/type/title/subject/publisher/grade/contentVersion/resource`。
4. 自动校验各教材的单元、课、条目数量，以及按该教材实际字段逐项一致（英文/释义，及存在时的词性、音标；汉字/声调拼音）；古诗文验证正文、注释位置和分段结果。
5. 产物随应用打包，安装后断网可浏览和学习。首版内容更新随发版进行，远程下载与内容热更新以后再做。

原始材料和可打印材料不是移动端内容源；`resources/raw` 与 Web 发布 JSON 如有差异，先记录并人工核验，禁止静默择一覆盖。

### 5.2 必须保留的旧标识

- 同步 `deckKey` 沿用页面路径去掉 `web/` 和 `.html`，例如 `textbooks/renai/english/grade7b-words`、`other/en20260704`。
- 英语旧条目键：`单元序号|课名|英文`，单元序号是 `DATA` 数组下标（从 0 开始，不是单元名），例如 `0|单词|lend`。仁爱、闽教教材的课名基本只有“单词/短语”，区分条目主要依赖该序号；`pref.unit` 同样是下标。提取脚本须按下标生成 `legacyKey`。
- 中文字词旧条目键：`课名|字词`。
- 古诗文当前 ID 由顺序生成：课组 `l1`、篇目 `l1-p1`、词语 `l1-p1-v1`、分段 `l1-p1-c1`。
- 英语插入、删除或重排单元，以及古诗文重排内容或改变分段，都会让旧键整体错位、误配进度。

建议新内容记录 `id + legacyKey`，古诗文同时保存明确的旧 ID 对照。历史导入时通过旧键映射到账号进度；新账号存储保持明确的内容 ID 和版本。内容更正、插入和重排都必须带映射迁移，无法匹配的旧记录保留在备份并报告，不自动认定为未学。

特别注意：仁爱七下和仁爱八年级两套页面导出都使用 `app: enwk`（其余英语页面的 app 各不相同），且旧导出可能只有 status，没有 deckKey 或偏好设置。导入时必须先选择目标教材并校验条目交集；有歧义时让用户选择，不能只依赖 app 字段判断教材。

## 6. 旧进度迁移

原生应用不能直接读取 Safari/Chrome 的 localStorage。新用户直接登录账号并开始学习；旧进度导入完全可选，导入失败不阻塞使用。登录用户可将历史数据导入自己的账号，游客可先导入本机后再选择迁入账号。提供以下两条历史导入路径：

**同步码迁移：** 用户先在原网页逐教材上传，再在 App 的“历史数据导入”中输入同一码，按 manifest 中已知 deckKey 逐个获取。现有接口没有教材列表查询，不能调用一个不存在的“拉取全部”接口。逐教材显示成功、无记录、失败并允许重试。

**导出文本迁移：** 用户从原页面导出，在 App 选择教材后粘贴或导入文件。词卡 v1 解析 `{app,version,status}`，并与 Web 端 `parseProgress` 一致地兼容不带包装的“键→状态”映射；古诗文解析 `{app,version,state}`；同步快照另用独立解析器，古诗文快照按 §2.3 的字段映射还原 `items/pieces/pref/roundCounter`。旧词卡导出不含偏好时恢复默认偏好，并明确提示只恢复学习标记。

导入固定流程：解析与大小检查 → schema/教材/条目校验 → 显示有效、未知、无效记录数及覆盖范围 → 本地备份 → 用户执行替换 → 单事务提交 → 标记待同步。失败必须保持原数据完整。首版不提供不明确的“智能合并”。

期中计划无现成同步和导出，本轮不迁移，其勾选记录留在网页。

移动端新备份格式至少包含 `schemaVersion/deckKey/contentVersion/kind/exportedAt/data`。完整备份可另含偏好，但默认不导出登录 token 或同步码。兼容 Web 的旧格式导出与移动端完整备份应命名区分。

## 7. 同步设计与共存策略

### 7.1 账号与进度接口

新 App 日常同步使用账号接口，旧 `/api/sync/*` 仅服务旧 Web 与历史导入。API 使用完整 HTTPS 地址，开发、测试、生产环境独立配置。下列为拟新增接口，不代表已有实现：

| 接口 | 用途 |
| --- | --- |
| `POST /api/auth/challenges` | 按手机号/邮箱和用途发送验证码，返回 challengeId 与重发间隔 |
| `POST /api/auth/login` | 校验登录 challenge，验证成功后登录或创建账号，返回用户与会话 |
| `POST /api/auth/refresh`、`POST /api/auth/logout` | 刷新或撤销会话 |
| `GET/PATCH /api/account/me` | 获取账号信息、修改昵称；手机号/邮箱不可直接 PATCH |
| `POST /api/account/identities/bind`、`/replace`、`/unbind` | 校验近期身份凭据与新目标验证码，管理登录方式 |
| `GET /api/account/sessions`、`DELETE /api/account/sessions/{id}` | 查看并撤销自己的设备会话 |
| `DELETE /api/account/me` | 二次验证后注销账号及删除所属云端数据 |
| `GET /api/progress` | 返回当前账号教材进度目录、内容版本和 revision |
| `GET/PUT /api/progress/{deckKey}` | 读取或条件更新一份教材进度 |

教材 deckKey 含 `/`，实现时必须约定路径编码或改用查询参数，不直接把它当作一个未经处理的路径段。绑定、换绑、解绑、注销等敏感操作使用短期、绑定用途的一次性验证凭据；登录验证码不能跨用途复用。

服务端新增 `users`、`user_identities`、`verification_challenges`、`sessions`、`user_progress`、`idempotency_records` 表；身份表对 `(type, normalized_identifier)` 建唯一约束，进度表对 `(user_id, deck_key)` 建唯一约束。手机号标准化为国际格式；邮箱使用明确、一致的比较规则，不自行删除加号后缀或点号合并地址。验证码校验、账号创建、身份绑定与唯一性检查需正确处理并发事务。

请求体上限、schema/内容版本校验、鉴权和访问日志脱敏在服务端统一实现；短信与邮件供应商失败允许重试并给出清晰状态。服务端保持 Python + SQLite，但现有标准库 `http.server` 不适合承载账号体系：新接口改用成熟框架（如 FastAPI/Starlette）与生产级 ASGI 服务，在 P0 确定选型，并组织路由、认证中间层、事务与数据库迁移。SQLite 保持 WAL，写事务使用 `BEGIN IMMEDIATE` 并设置忙等待，验证码消费、账号创建与身份绑定在同一写事务内完成。旧 `/api/sync/*` 可以继续由原服务提供，或迁入新框架后做回归；不直接将现有同步码拼到新账号上充当登录。

### 7.2 可靠自动同步

`GET /api/progress/{deckKey}` 返回快照和服务端递增整数 revision；PUT 带 `baseRevision` 和 `requestId`。服务端在事务内比较 revision，匹配后更新并递增，不匹配返回 409。空记录使用明确初始 revision；相同用户、requestId 和相同请求重试返回原结果，同 ID 不同请求返回冲突。

处理流程：本地保存并递增 local_revision → 以 `server_revision` 为 baseRevision 条件上传 → 成功后推进 acked_revision、更新 base_json 与 server_revision；返回 409 时拉取云端最新快照进入合并。

冲突合并：

- **词卡：** 进度是“条目键 → 状态”映射，用 `base_json` 做逐条三方合并。只有一端相对基线改动的键直接采用该端；两端改成相同值不算冲突；只有两端把同一键改成不同值（含一端删除，即重置为未学）才是真冲突。真冲突逐条或整体让用户选择本机或云端，其余自动合并后基于最新 revision 再提交。偏好 `pref` 以本机为准，不参与冲突提示。
- **古诗文：** 记录含阶段、计数和轮次计数，首版不做逐条合并；冲突时保留两份快照，显示教材、更新时间和主要进度差异，由用户整体选择本机或云端。
- 任何情况下都不能简单取最高掌握度，否则会抹掉用户主动重置或改为需复习的操作；合并或选择覆盖前都先写入备份。

自动触发点为登录恢复完成、本地变更后短暂防抖、回到前台和手动重试。首次登录先读取云端目录，再处理游客数据；后续登录本地有待传修改时不得直接覆盖。切后台先持久化，网络上传尽力而为，不依赖应用终止回调。

上传中继续作答不能清除新变更；会话失效暂停队列，重新登录原账号后续传；切换账号取消旧任务并隔离迟到响应。429 有界退避，网络超时允许幂等重试，403/账号注销不得无限重试。“已同步”只在对应本地 revision 得到成功确认后显示。

### 7.3 旧 Web 与同步码的过渡

账号进度与旧同步码进度使用独立存储命名空间。输入旧同步码只读取旧快照，预览后复制到当前账号；它不能访问、覆盖或修改账号进度，也不能作为账号找回凭证。首版不自动双向桥接，旧 Web 后续变化不会自动进入账号，界面必须说明“历史导入为一次性复制”。

因此旧 Web 的无条件 PUT 不会绕过账号进度的 revision 保护。未来如需要 Web 和 App 共享同一账号进度，需给 Web 增加同一账号登录，并改用带鉴权与 revision 的新接口；该 Web 升级单独排期。迁移期间可以继续用旧页面学习，但要明确两套进度不会自动互通。

新数据库与端点采用向后兼容迁移，部署前备份并验证恢复，旧 `/api/sync/*` 保持回归。新用户不生成同步码，账号内无需用户逐教材手动上传/拉取。

## 10. 测试与验收

### 内容与兼容

- 五套英语、中文字词、古诗文内容数量、文本和分组与提取基线一致；字段缺省（无词性、有音标）的教材展示正确。
- 英语 `legacyKey` 按单元下标生成，与 Web 真实导出逐键一致；同一单词跨单元不串进度；古诗文重排升级映射准确；未知旧键有报告和备份。
- 旧词卡（含不带包装的映射格式）、古诗文、同步快照（词卡与古诗文两种结构）分别导入；错误教材、损坏 JSON、过大文件不会改写本地。
- 导出再导入后状态相等；恢复备份可回到导入/重置前。

### 学习流程

- 翻面、双向学习、范围筛选、状态标记、计数、空范围、最后一张、位置恢复均正确。
- `hashString` 对含中文与标点的输入与 Web 输出逐值一致；固定 `roundCounter` 与状态下，轮次队列和选项顺序与 Web 完全一致。
- 古诗文以固定样例对照旧算法；答错、提示、跨轮正确、重试插入、轮次结束覆盖完整。
- 全文浏览不提升掌握度；切后台、进程被杀和内容升级后的恢复不重复提交答案。

### 账号与登录

- 手机号、邮箱两种渠道均能验证登录及首次创建账号；错误、过期、重复消费、重发和超限验证码处理正确。
- 绑定第二种登录方式后两种方式进入同一账号；重复绑定冲突、并发创建、换绑与解绑保护符合规则。
- 登录恢复云端进度；游客迁入有确认和备份；账号 A/B 切换及迟到网络响应不会串数据。
- token 刷新、过期、退出、远程下线、账号注销生效；未授权请求和修改 user_id 的越权请求被拒绝。
- 验证码供应商失败不会假装已发送；正式构建不含测试验证码、发送密钥或敏感日志。
- 经 Nginx 访问时限流按真实客户端 IP 生效，伪造的转发头不能绕过；服务重启后限流计数仍有效；未通过人机验证不能发送验证码。
- 首次启动展示隐私政策与用户协议并记录同意；未满 14 周岁走监护人同意流程。

### 同步与设备

- 断网启动、离线作答、重启、恢复网络后进度不丢；未上传时绝不显示已同步。
- 上传中再次作答、响应丢失重试、切换账号、并发上传、409、429、服务端失败均有覆盖。
- 词卡三方合并：两端改不同条目自动合并；同一条目改成不同值（含重置）才提示冲突；合并前有备份。
- 新账号进度与旧同步码存储隔离；旧码一次性导入不会授予账号访问权限；同账号双设备条件更新可正确检出冲突。
- Android/iOS 真机验证 TTS、剪贴板拒绝/失败、文件导入分享、返回键、键盘、安全区、大字号和长文。
- 以签名 release 构建验收；安装升级后数据库与本地进度保持，卸载造成的本地数据删除有备份恢复路径。

完成标准：全部纳入范围的页面均有原生实现；手机号/邮箱登录与账号管理可用；核心学习离线可用；登录后恢复进度；旧进度可选导入且可核验恢复；多设备同步没有静默覆盖；双端签名构建可交付。

## 11. 构建、发布与回退

- Mobile 使用独立 package.json 和锁文件；CI 执行类型检查、内容校验、纯逻辑测试和构建检查。
- 采用 development / preview / production 环境；可以选择 EAS Build 或本地原生构建，不强制引入云构建付费服务。
- Android 先提供内测 APK，商店发布准备 AAB 和签名密钥保管；iOS 根据 Apple 开发者账号条件使用 TestFlight 等分发方式。具体商店要求在实施发布时核验。
- 原生依赖或权限变化需要重新构建安装包；不能把远程 JS 更新当作任意原生升级途径。
- Nginx 新增 `/api/auth/`、`/api/account/`、`/api/progress` 转发，透传 `X-Real-IP` / `X-Forwarded-*`，按接口设置请求体上限；保持现有 `/api/sync/` 配置不变。
- 服务端先部署账号与进度接口并备份数据库，完成短信/邮件真实发送及账号隔离验证后再发布 App；旧 Web 保持独立，账号版 Web 后续排期。
- App 问题优先回退客户端版本并保留数据库兼容；服务端回退需保留已创建账号、身份绑定和进度数据，不退回同步码认证或开放无鉴权写入。
- 至少保留一个发布周期的 Web 学习入口作为学习替代路径；不自动清理旧浏览器进度。

## 13. 开工顺序

第一天同时启动 App 备案、短信资质和隐私合规文本等外部事项。开发上先建立内容清单、可选旧进度 fixtures（含英语按单元下标的真实键）和兼容映射，确定服务端框架并验证邮件发送链路；然后完成“邮箱登录 → 一套英语教材 → 离线学习 → 账号同步 → 换机登录恢复”的纵向闭环。验证通过后补齐其他词卡，再接入手机号登录、账号管理与历史导入，然后迁移古诗文，最后完成同步加固。

这一顺序可以尽早验证迁移成本，并把数据丢失、ID 错配和原生能力差异暴露在全面开发之前。
